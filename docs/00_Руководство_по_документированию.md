# Руководство по документации проекта

## 1. Цель документа
Этот документ фиксирует единые правила ведения проектной документации.
Он отвечает на вопросы **как документируем**, **в какой структуре**, **с какой степенью детализации**, **как связываем документы между собой**, **как проверяем актуальность и непротиворечивость**.

Документ описывает **процесс**, а не содержание конкретной игры.

---

## 2. Принципы документации

### 2.1 Однозначность
- Любое утверждение должно интерпретироваться одинаково любым участником команды.
- Избегать формулировок «примерно», «как-нибудь», «по ситуации» без явных критериев.
- Если есть варианты поведения — перечислять их как отдельные сценарии с условиями выбора.

### 2.2 Трассируемость (прослеживаемость)
- Любой документ нижнего уровня обязан ссылаться на родительский документ.
- Любое требование должно иметь уникальный идентификатор (ID).
- По ID должно быть возможно подняться вверх (к цели) и спуститься вниз (к реализации).

### 2.3 Атомарность
- Одна запись = одно требование/одно правило/одна операция.
- Не смешивать в одном пункте UX, логику, данные и реализацию без явных подзаголовков.

### 2.4 Проверяемость
- У каждого требования должны быть критерии готовности (Definition of Done для документа).
- Требование считается корректным только если его можно проверить: вручную, тестом, симуляцией или ревью.

### 2.5 Версионирование
- Документы изменяются только с фиксацией версии и краткого журнала изменений.
- Значимые изменения не редактируются «молча».

### 2.6 Минимум дублирования
- Один источник истины на одну сущность.
- Повторять информацию можно только в виде ссылки/выдержки, но не как независимый текст.

### 2.7 Разделение «что» и «как»
- На верхних уровнях фиксируется **что должно быть достигнуто**.
- На нижних — **как именно это делается в коде/данных/UX**.

---

## 3. Иерархия документов

Документация ведётся в 5 уровнях.

### L0 — Методология документации (этот документ)
**Назначение:** единые правила ведения документации проекта.

### L1 — Архитектура проекта и дизайн верхнего уровня
**Назначение:** целостное описание игры как системы.
**Содержит:** видение, границы проекта, ключевые подсистемы, продуктовые и технические принципы.

### L2 — Расширяющие документы по разделам L1
**Назначение:** детализировать каждую ключевую подсистему.
**Примеры:** прогрессия, экономика, боёвка, AI, мир, нарратив, техническая архитектура.

### L3 — Операционные спецификации
**Назначение:** описать отдельные операции/сценарии и участвующие данные.
**Фокус:** последовательность шагов, условия входа/выхода, ошибки, ограничения, состояние данных.

### L4 — Исполнительные спецификации
**Назначение:** два целевых представления L3-логики:
1. **UX-спецификация** (для дизайнеров/художников/аниматоров).
2. **Code-спецификация** (для программистов/тестировщиков).

## 4. Структура папок

Рекомендуемая структура в репозитории:

```text
docs/
  00_Руководство_по_документированию.md
  10_L1_Архитектура_и_дизайн_верхнего_уровня/
  20_L2_Подсистемы/
  30_L3_Операционные_спецификации/
  40_L4_UX_и_Code_спецификации/
  90_Глоссарий_и_реестры/
  99_Архив/
```

Правила:
- Нумерация префиксами (`00`, `10`, `20`...) обязательна.
- Документы не удаляются без архивации в `99_Архив`.
- Черновики помечаются суффиксом `_draft`.

---

## 5. Правила именования

### 5.1 Файлы
Формат:

```text
<уровень>_<домен>_<сущность>_v<major>.<minor>.md
```

Пример:

```text
L3_combat_hit-resolution_v1.2.md
```

### 5.2 Идентификаторы требований
Формат:

```text
REQ-<LEVEL>-<DOMAIN>-<NNNN>
```

Пример:

```text
REQ-L3-COMBAT-0042
```

### 5.3 Идентификаторы сценариев/операций
Формат:

```text
OP-<DOMAIN>-<NNNN>
```

Пример:

```text
OP-ECON-0017
```

## 6. Обязательные секции для каждого документа

Каждый `.md` документ уровней L1–L4 должен содержать:

1. **Metadata**
   - ID документа
   - Уровень (L1/L2/L3/L4)
   - Статус (`draft`, `review`, `approved`, `deprecated`)
   - Версия
   - Автор
   - Дата создания
   - Дата последнего изменения

2. **Цель**
   - Зачем документ существует
   - Какие решения фиксирует

3. **Границы**
   - Что входит
   - Что не входит

4. **Зависимости**
   - Родительские документы
   - Дочерние документы
   - Внешние ограничения

5. **Содержание уровня**
   - Для L1: системный обзор
   - Для L2: детальная подсистема
   - Для L3: операции и данные
   - Для L4: UX и/или кодовая реализация

6. **Критерии готовности**
   - Чеклист полноты
   - Проверки непротиворечивости

7. **История изменений**
   - Версия
   - Что изменено
   - Почему

---

## 7. Связность между уровнями

### 7.1 Правило «1 вверх, N вниз»
- Каждый документ (кроме L0) обязан ссылаться минимум на 1 родительский.
- Каждый документ может порождать N дочерних.

### 7.2 Матрица трассировки
Для всех требований ведётся реестр `docs/90_Глоссарий_и_реестры/traceability_matrix.md`, где фиксируется:
- REQ ID
- Источник (документ + раздел)
- Производные REQ/OP
- UX-артефакт
- Code-артефакт
- Тест(ы)
- Статус

### 7.3 Запрет «висячих требований»
Любое требование без дочерней реализации (UX/Code) или без причины отклонения считается дефектом документации.

---

## 8. Правила описания операций (L3)

Каждая операция оформляется как карточка:

1. `OP ID`
2. `Название`
3. `Цель операции`
4. `Акторы` (игрок, NPC, сервер, система мира и т.д.)
5. `Предусловия`
6. `Триггер`
7. `Основной поток`
8. `Альтернативные потоки`
9. `Исключения и ошибки`
10. `Постусловия`
11. `Изменяемые данные`
12. `События/сигналы`
13. `Нефункциональные ограничения` (время отклика, нагрузка, детерминизм)
14. `Связанные UX и Code спецификации`
15. `Тест-кейсы (минимальный набор)`

---

## 9. Правила для UX- и Code-спецификаций (L4)

### 9.1 UX-спецификация
Обязательные блоки:
- пользовательская цель;
- контекст использования;
- экран(ы)/состояния интерфейса;
- поведение элементов;
- фидбек системы (визуальный/аудио/тактильный);
- доступность;
- телеметрия UX-событий;
- критерии приемки.

### 9.2 Code-спецификация
Обязательные блоки:
- границы модуля;
- входы/выходы;
- структуры данных;
- инварианты;
- алгоритм/состояния;
- обработка ошибок;
- логирование/метрики;
- тестовая стратегия;
- критерии приемки.

### 9.3 Синхронизация UX и Code
- UX и Code документы ссылаются на один `OP ID`.
- Изменение UX-поведения без ревизии Code-спеки запрещено.
- Изменение логики кода без проверки UX-влияния запрещено.

## 10. Глоссарий и единый словарь

- Все термины фиксируются в `docs/90_Глоссарий_и_реестры/glossary.md`.
- Запрещено использовать термин в требованиях до его определения в глоссарии.
- Для терминов указываются синонимы и запрещённые варианты написания.

## 11. Процесс изменений

### 11.1 Типы изменений
- `patch` — уточнения формулировок без изменения смысла.
- `minor` — добавление новых требований без поломки существующих связей.
- `major` — изменение логики/контракта, требующее пересмотра дочерних документов.

### 11.2 Порядок изменения
1. Создать запись в истории изменений.
2. Обновить документ-источник.
3. Обновить traceability matrix.
4. Проверить затронутые дочерние документы.
5. Зафиксировать статус ревью.

### 11.3 Статусы документа
- `draft` — черновик.
- `review` — на проверке.
- `approved` — принят, используется как источник истины.
- `deprecated` — заменён, хранится для истории.

---

## 12. Качество документации (Definition of Done)

Документ считается готовым, если:
- заполнены все обязательные секции;
- есть ID и версия;
- есть связи вверх/вниз;
- нет противоречий с родительскими документами;
- термины согласованы с глоссарием;
- требования проверяемы;
- добавлены/обновлены ссылки в traceability matrix.

## 14. Правила ревью

- Нельзя утверждать документ самому себе без второго чтения (минимум через 24 часа).
- Любой `major` требует ревью всех затронутых документов L+1 и L+2.
- Замечания ревью фиксируются в конце документа отдельным блоком `Review Notes` до их разрешения.

---

## 15. Практика ведения в репозитории

- Один смысловой коммит на одно логическое изменение документации.
- Сообщение коммита: `<docs>: <краткое действие>`.
- Перед merge обязательно проверить ссылки между документами и битые якоря.
