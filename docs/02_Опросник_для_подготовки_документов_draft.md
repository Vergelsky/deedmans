## 1. Назначение
Опросник нужен, чтобы ассистент стабильно собирал все входные данные перед генерацией документа
и не выпускал неполные или противоречивые версии.

## 2. Правило использования
- Ассистент проходит опросник сверху вниз.
- Пропуск вопроса допускается только если:
  1) вопрос нерелевантен типу документа;
  2) есть явное решение владельца проекта «на усмотрение ассистента».
- Все допущения фиксируются явно в блоке `Допущения` документа.

## 3. Базовый блок (для любого уровня)
1. Какой документ создаём/обновляем (ID/название/уровень)?
2. Какова цель документа (какое решение он фиксирует)?
3. Границы документа (что входит / что не входит)?
4. На какие родительские документы он опирается?
5. Какие дочерние документы он должен породить?
6. Какие термины и определения обязательны?
7. Какой целевой статус после текущей итерации (`draft`, `review`, `approved`)?

## 4. Блок для L1 (верхний уровень)
1. Какие ключевые домены системы включены?
2. Какие домены сознательно исключены на текущем этапе?
3. Какие продуктовые принципы являются обязательными?
4. Какие технические ограничения уже известны?
5. Какие риски масштаба и состава фич считаем критичными?

## 5. Блок для L2 (подсистема)
1. Какая подсистема декомпозируется?
2. Каковы её входы/выходы на уровне системы?
3. Какие зависимости с соседними подсистемами?
4. Какие инварианты и ограничения обязательны?
5. Какие операции нужно спустить в L3 в первую очередь?

## 6. Блок для L3 (операции)
1. OP ID и краткая цель операции.
2. Акторы.
3. Предусловия.
4. Триггер.
5. Основной поток.
6. Альтернативные потоки.
7. Ошибки/исключения.
8. Постусловия.
9. Изменяемые данные.
10. События/сигналы.
11. Нефункциональные требования.
12. Какие L4 UX/Code документы создаются по этой операции?

## 7. Блок для L4 UX
1. Какая пользовательская цель закрывается?
2. В каком контексте используется сценарий?
3. Какие состояния интерфейса обязательны?
4. Какие состояния ошибок и пользовательский фидбек?
5. Какие UX-метрики/телеметрию собираем?
6. Какие критерии приемки UX считаются достаточными?

## 8. Блок для L4 Code
1. Каковы границы модуля и интерфейса?
2. Какие входы/выходы и контракты?
3. Какие структуры данных и инварианты?
4. Какой алгоритм/машина состояний?
5. Какие типы ошибок и стратегия обработки?
6. Какие логи/метрики/трейсинг обязательны?
7. Какая тестовая стратегия (unit/integration/e2e)?
8. Какие критерии приемки кода?

## 9. Проверка готовности перед финализацией
Чек-лист:
- [ ] Тип документа подтверждён.
- [ ] Границы определены.
- [ ] Все блокирующие вопросы закрыты.
- [ ] Допущения явно перечислены.
- [ ] Связанные документы определены.
- [ ] Термины согласованы с глоссарием.
- [ ] Критерии готовности сформулированы.

## 10. Формат краткого статуса в диалоге
Перед началом каждой новой итерации ассистент публикует:
- `Этап: ...`
- `Нужно от тебя: ...`
- `Дальше сделаю: ...`
